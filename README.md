# Balance Tracker

Мультитенантный сервис учёта крипто-портфеля: собирает балансы с бирж и on-chain кошельков,
приводит их к единой схеме, хранит историю и отдаёт её через REST API и Telegram-бота с
тарифами и уведомлениями.

Проект интересен не «подключением к бирже», а тем, что делает с полученными данными:
нормализация разных источников, проверка целостности до записи, кэш с ревалидацией,
идемпотентные задания синхронизации и лимиты тарифа, которые применяются в сервисном слое,
а не в UI.

## Задача

Пользователь держит активы на нескольких биржах и в нескольких сетях. Чтобы увидеть
портфель целиком, ему нужно вручную свести балансы, пересчитать в доллары и вспомнить, что
было вчера. Биржевые API при этом отдают разные форматы, часть эндпоинтов недоступна через
готовые библиотеки, а периодическая синхронизация легко превращается в дубли транзакций и
двойной учёт зеркальных счетов (spot/futures в unified-режиме).

## Как устроено

```
bot (aiogram)  ─┐
                ├─► FastAPI ──► services ──► repositories ──► PostgreSQL
REST клиенты ───┘                  │                            ▲
                                   ├─► ccxt_manager  ──► биржи  │
                                   ├─► exchange_rest ──► REST   │
                                   ├─► okx_wallet / tron_ton / sui
                                   └─► response_cache (L1 + Redis)
                     worker / scheduler ──► refresh_orchestrator ──► sync_job_service
```

Поток одного обновления:

1. `RefreshOrchestrator` ставит задание (`SyncJob`) с атомарной дедупликацией — два
   одновременных запроса не создают дубль.
2. `BalanceService` забирает активные интеграции организации, группирует их по типу
   источника и тянет балансы параллельно (ограниченный семафор).
3. Каждый источник отвечает схемой `ServiceBalanceSchema`
   (`app/schemas/balance.py`) — либо ошибкой, которая фиксируется в статусе провайдера.
4. `balance_integrity` проверяет payload до записи: пустой «положительный» баланс,
   расхождение суммы активов и итога, деградировавшие ответы. Невалидное — отклоняется.
5. `BalanceRepository` пишет снапшот, а `parse_balances` в боте строит из него
   spot/futures/dex-разрезы и человекочитаемые метки сервисов.

## Что реально реализовано

- **Источники.** CCXT-путь для основных бирж; прямые REST-гейтвеи там, где CCXT-путь
  сломан (BitMart); кошельки — OKX Wallet через локальный `debank-sdk`, TRON/TON, SUI.
- **Мультитенантность.** `organization_id` в каждой таблице, JWT-аутентификация для API,
  сервисные ключи для межсервисных вызовов, memberships и роли.
- **Retención истории.** `balances` + `balance_history`, точки для графика с интервалами,
  fill-forward, PnL-метрики в `/dashboard/summary`.
- **Тарифы и биллинг.** Планы, лимиты (CEX-аккаунты, кошельки), промокоды, счета,
  вебхуки провайдеров, леджер.
- **Уведомления.** События по изменениям портфеля и транзакциям, настройки на пользователя,
  курсоры, чтобы не отправлять одно и то же дважды.
- **Наблюдаемость.** Prometheus-метрики, `/metrics`, `/health`, request-context middleware,
  аудит-лог сервисных действий.
- **Нагрузочные тесты.** k6-сценарии (`loadtests/steady.js`, `burst.js`, `degraded.js`) для
  read-path API и деградации.

## Инженерные решения

**Решение: слой гейтвеев над биржами вместо прямых вызовов CCXT в сервисах.**
Зачем: формат ответов и поведение API у бирж различаются, а часть путей требует обхода
библиотеки (например, BitMart, где CCXT-путь возвращает неполные данные). Гейтвей прячет
это за одним интерфейсом `fetch_balance`.
Компромисс: два пути сопровождения — при обновлении биржевого API править приходится
гейтвей, а не только библиотеку.

**Решение: проверка целостности баланса до записи.**
Зачем: «пустой, но положительный» баланс или итог, не совпадающий с суммой активов, ломает
историю и PnL сильнее, чем отсутствие данных; такой payload отклоняется и уходит в статус
ошибки, а не в БД.
Компромисс: часть легитимных краевых ответов требует явного исключения (например,
портфельные источники, где итог не равен сумме токенов).

**Решение: идемпотентные задания синхронизации.**
Зачем: кнопка «обновить» и планировщик запускаются параллельно; дедупликация на уровне
уникального активного job исключает двойную нагрузку на биржи.
Компромисс: отложенный повтор возможен только после завершения предыдущего задания.

**Решение: кэш L1 в процессе + опциональный Redis, с ревалидацией устаревших значений.**
Зачем: экраны бота и API читают портфель часто, а обновление с биржи — дорогое; при
`enable_ccxt_stale_revalidate` устаревшее значение отдаётся сразу и обновляется в фоне.
Компромисс: данные могут быть не «свежими на миллисекунду»; это отражено в интерфейсе
через метку времени.

**Решение: лимиты тарифа в сервисном слое (`entitlements_service`).**
Зачем: проверка в UI обходится любым прямым вызовом API; лимит должен жить там, где
создаётся сущность.
Компромисс: цена ошибки в политике выше — неверный лимит блокирует легитимное действие.

**Решение: единая конфигурация исходящего прокси (`OUTBOUND_PROXY_URL`).**
Зачем: часть источников доступна только через egress-прокси, и конфигурация должна быть
одной для API, воркеров и бота (у бота — через `proxychains` в entrypoint).
Компромисс: одобренный прокси-хост — это deploy-настройка (`OUTBOUND_PROXY_HOST`), её нужно
задавать в окружении; в образе она не хранится.

## Стек

| Слой | Технологии |
|---|---|
| API | Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2 (async), Alembic |
| Данные | PostgreSQL (asyncpg), SQLite (aiosqlite) для локального режима, Redis |
| Биржи | ccxt, aiohttp REST-гейтвеи, ccxt.pro |
| Кошельки | `debank-sdk` (локальный сервис), TRON/TON, SUI |
| Бот | aiogram, single-message UI, i18n |
| Инфраструктура | Docker Compose (postgres, redis, debank-sdk, api, worker, scheduler, bot) |

## Быстрый старт

### Демо без ключей и без сети

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
python scripts/demo_sqlite.py
```

Скрипт создаёт отдельный SQLite-файл, поднимает схему, записывает синтетические балансы
через те же репозитории, что и production-путь, и печатает сводку тем же кодом, которым её
строит бот (`parse_balances`). Ни одна биржа не опрашивается.

### Полный стек

```bash
cp .env.example .env      # заполнить секреты и, при необходимости, OUTBOUND_PROXY_*
docker compose up --build
```

По умолчанию `DATABASE_USE_SQLITE=false`; для локального запуска без PostgreSQL включите
SQLite (`DATABASE_USE_SQLITE=true`, `SQLITE_DATABASE_URL=***REMOVED***`).
API слушает `127.0.0.1:8001`, схема — `/docs`.

### Тесты

```bash
pytest                # 285 тестов, ~45 секунд, без сети и без внешней БД
```

## API

```bash
TOKEN="<JWT>"
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8001/api/v1/balances | jq
curl -s -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:8001/api/v1/history?service=binance&limit=10" | jq
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8001/api/v1/dashboard/summary | jq
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8001/api/v1/refresh
```

Основные группы: `/api/v1/balances*`, `/api/v1/history*`, `/api/v1/integrations*`,
`/api/v1/transactions*`, `/api/v1/billing*`, `/api/v1/notifications*`, `/api/v1/admin*`,
`/health`, `/metrics`.

## Структура

```text
app/
  routers/        # HTTP-контракты: balances, integrations, transactions, billing, admin
  services/       # балансы, биржи, кошельки, тарифы, биллинг, уведомления, целостность
  repositories/   # доступ к БД, снапшоты, история, транзакции
  models/         # ORM-модели (организации, интеграции, балансы, биллинг, аудит)
  core/           # конфигурация, БД, безопасность, RBAC, HTTP-хелперы, middleware
bot/              # Telegram UI: экраны, клавиатуры, i18n, уведомления
debank-sdk/       # локальный сервис для on-chain данных кошельков
alembic/          # 10 миграций
loadtests/        # k6: steady, burst, degraded
scripts/          # демо, миграция sqlite→postgres, probes, research
tests/            # регрессионный набор
```

## Что происходит при сбоях

- **Биржа недоступна.** Источник помечается ошибкой (`integration_status`), остальные
  продолжают обновляться; задание получает статус `partial` или `failed`.
- **Провайдер деградирует.** После серии ошибок открывается circuit breaker: запросы к нему
  временно пропускаются, чтобы не жечь лимиты.
- **Payload не проходит проверку целостности.** Запись не создаётся, ошибка фиксируется,
  история остаётся согласованной.
- **Прокси-соединение оборвалось.** REST-гейтвей повторяет запрос напрямую (без прокси),
  если политика источника это допускает.
- **Дублирующий запуск обновления.** Дедупликация заданий возвращает уже активную запись
  вместо второй синхронизации.

## Ограничения

- Демо полностью синтетическое; реальные балансы требуют ключей бирж и (для кошельков)
  работающего `debank-sdk`.
- On-chain данные приходят из публичных web-API, а не из индексирующих узлов: схему ответа
  может изменить третья сторона.
- PostgreSQL — основной режим; SQLite удобен для локального запуска и тестов, но не для
  конкурентной записи.
- Ограничения планов заданы политикой в коде; изменение лимитов — изменение политики и
  тестов.
- Репозиторий не содержит CI-workflow: тесты запускаются локально (`pytest`).

## Разработка с AI

AI использовался как инструмент: черновики сервисов и тестов, рефакторинг, разбор
недокументированных API, документация и отладка. Результат проверялся тестами
(285 тестов, включая контракты API, изоляцию тенантов и поведение кэша), ревью диффов и
ручной проверкой на локальном стеке; реверс-инжиниринговые скрипты вынесены в
`scripts/research/` и не участвуют в рантайме и тестах.
