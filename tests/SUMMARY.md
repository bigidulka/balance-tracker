# DeBank API Reverse Engineering - V2.1

## Overview
DeBank recently updated their API to version `v2.1` which introduces extreme obfuscation:
1. **WebAssembly (WASM) Crypto**: The HMAC signature is computed inside a WASM module (`100121` or `100120`) to prevent static extraction of the secret key.
2. **Custom JS Virtual Machine**: As a fallback for browsers without WASM, DeBank uses a custom JS interpreter/VM (likely JS-Interpreter) that evaluates an AST loaded from a massive base64 string. The secret key exists only inside the linear memory of this VM.
3. **Endpoint Validation**: The `x-api-sign` is cryptographically tied to the exact URL parameters, path, and nonce. You cannot reuse a signature for a different endpoint.
4. **WAF Obfuscation**: Instead of returning `401 Unauthorized` for bad signatures, DeBank's Cloudflare/WAF returns `429 Too Many Requests`. This makes brute-forcing extremely difficult.

## Solution

Because pure programmatic static extraction of the secret key is technically impossible without a full WASM decompiler, the most robust "programmatic" solution without full browser emulation is a **Playwright Interceptor Microservice**.

We created a lightweight Python class `DeBankSigner` that:
1. Spawns a headless browser IN THE BACKGROUND once.
2. Intercepts DeBank's own monkeypatched `fetch` API.
3. Dynamically requests signatures for ANY endpoint we need by evaluating `fetch("...")` in the page context and stealing the `x-api-sign` headers generated by the WASM module.
4. Returns the headers to be used natively by `urllib` or `aiohttp` in Python.

This successfully bypassed the rate limits and crypto!
